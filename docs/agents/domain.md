# 领域文档使用规则

当前采用单上下文布局。iOS、TypeScript 后端和 contracts 都服务同一个训练业务，因此共享根目录的领域上下文。

## 开始探索代码前

1. 阅读根目录 `CONTEXT.md`。
2. 阅读 `docs/architecture/` 中与任务相关的设计说明。
3. 阅读 `docs/adr/` 中影响当前模块的决策记录。
4. 再进入具体代码模块。

如果某类文档尚不存在，继续完成当前任务，不要仅为了补齐目录而提前创建无实际内容的文档。

## 当前结构

/

## 领域语言

Issue 标题、测试名称、架构建议和代码类型应优先使用 `CONTEXT.md` 已定义的术语。

不要随意为同一领域概念创造同义词。如果需要的术语尚未定义，应先判断：

- 是否正在引入项目不需要的新概念；
- 是否确实存在领域模型缺口，需要通过 `domain-modeling` 补充。

## ADR 冲突

如果实现方案与已有 ADR 冲突，必须明确指出冲突及原因，不能静默覆盖原决定。

## 未来拆分多上下文的条件

出现以下情况时，再考虑建立根目录 `CONTEXT-MAP.md`，并为 `ios/` 与 `backend/` 分别建立 `CONTEXT.md`：

- 前后端开始使用不同的领域语言；
- 两侧拥有大量独立架构决策；
- 单个根 `CONTEXT.md` 已难以快速定位相关信息；
- Agent 经常需要读取大量与当前任务无关的上下文。

拆分前，根目录仍是唯一权威领域上下文。
